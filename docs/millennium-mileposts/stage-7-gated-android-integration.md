## Application boundary

`MilepostIntegration.PRODUCTION` is the single application gate: an immutable instance constructed with `enabled=false`, no approved catalogue revision/hash/fingerprint and no approved evaluator. There is no preference, imported backup, intent, remote configuration, debug-build switch, public constructor, production factory or mutable global override. Enabling requires a future reviewed source change, compatible evaluator pin and approved catalogue envelope; this PR does not supply them. Unit tests reflect the private constructor to create independent instances tied to random fixture databases and synthetic catalogue pins. They never replace or mutate PRODUCTION, even when exercising the enabled screen/worker path.

The gate protects the existing JobService's scheduler **and** job entry (including stale OS deliveries), the worker coordinator, screen mounting/refresh and page readers. When disabled no new screen section is mounted, job scheduled, database opened or derivation performed. Existing general award and celebration preferences remain independent and unchanged; milepost awards remain Stage 5's seven derived SQLite states, consumed through their committed receipt rather than copied into another engine. No manifest, database schema or production migration is added.

The gate verifies exact approved revision, source SHA and immutable installed content fingerprint, plus evaluator compatibility, before processing, reads and history pages. The fingerprint covers physical eligibility, designer verification and aliases. The existing transactional installer rejects content changes under an unchanged pin. There is no downloader, installer, approval promotion or JSONL reader in this integration. Missing/incompatible/unverified reference data yields no presentation or awards. All **889** actual revision-1 candidates still have `eligible_count=0` and `validated_physical_count=0`; none is installed or approved. The actual candidate SHA remains `63d9772ede9cf59ad7aa882e838b2032a133cc322a01740d6ff336cfa97e2377`.

## Screen and lifecycle

`AchievementsActivity` retains its existing bottom navigation, content container and celebration system. It mounts the Stage 6 native view through `MilepostScreenIntegration` only inside the gate. No new Activity or navigation stack is introduced. Its normal two-second evidence refresh and resume/pause callbacks drive compact reads, cancellation, detach and persistence. The view is an inline section in the existing achievements scroll architecture; its own existing scroll surface is reused. Touch/scroll ergonomics on physical devices remain acceptance work.

The adapter creates the existing Stage 6 presentation store, reads its acknowledgement cursor, and obtains only a **current**, committed Stage 5 receipt off the UI thread. It rejects deliveries after pause, replacement requests, capture, archive/NCN publication changes and NCN-evidence changes. Runtime replay and acknowledgement actions receive an additional cheap live archive/NCN freshness fence. Updates reuse the current view when the receipt changes. Stale/unavailable inputs hide the section; corrupt presentation state preserves the original record and logs unavailability rather than resetting it. Periodic reads retry safely. No full archive or geometry is retained by the screen adapter.

The existing mystery cards, designer identities, collective, all Harrow stages, historical summary, paged history, withdrawal/reinstatement, static replay, pause/dismiss and durable per-user state are reused. Ordinary award modals never receive these awards. Stage 6's static controls, spoiler-safe labels, 48dp targets, focus order and text-scaling coverage remain in the regression selection. No final artwork, map pins, sound or animation is added.

## Work scheduling, concurrency and capture

On achievement-screen pause the existing job scheduler is invoked, but returns immediately while disabled. Future enabled jobs retain idle/charging, nonperiodic/nonpersisted constraints. The worker uses the existing serial `ScreenDataLoader` archive-heavy executor, not a new parallel pool. Its explicit two-second cooperative deadline and OS stop/cancellation token feed Stage 4/5; interrupted proof pages remain durable. A fresh coordinator repeats the Stage 5 whole-archive metadata freshness pass, preserves incremental proof pages, and derives only after completion against the current NCN snapshot. SQLite writer/archive/NCN publication order remains Stage 5's implementation.

An instance-wide exclusive lease prevents milepost processing and mounted presentation from running together. Screen entry does not block the UI while processing: a later normal refresh retries. Pause hides/detaches the native view, invalidates callbacks and queues lease release **after** earlier serialized reads/pages have exited. Workers defer while a screen holds the lease. This prevents active overlap of the known geometry-heavy reconciliation and native replay workloads, but does not prove ART headroom or eliminate the need to collect previously detached views. General map, NCN and capture memory still needs physical profiling.

Capture guards latch recording starts; worker cancellation rolls back incomplete publication. Stage 6 independently pauses/persists reveal and suppresses summary/reveal actions during capture. Stopping capture does not auto-continue replay. The integration's read/detail callbacks additionally reject capture interruptions. There is no UI-thread reconciliation, catalogue query or full-archive scan. Existing synchronous SharedPreferences writes for compact presentation state are unchanged.

A two-second cooperative deadline is not a hard SQL preemption or demonstrated device timing budget. Repeated restarts repeat the metadata freshness sweep; physical acceptance must establish convergence and responsiveness with a large private archive before any activation. This stage does not claim to solve the existing Stage 4 high transient peak.

## Reproducible physical-device acceptance protocol — NOT PERFORMED

This protocol requires a separately authorised private test build with an isolated synthetic fixture configuration, approved distribution and backup of the tester's archive. It does not authorise changing the production gate or using the unapproved candidate inventory. Use an isolated app/data profile; do not import synthetic journeys into the user's real achievement database.

Use `adb shell dumpsys meminfo <package>` and Android Studio Memory Profiler/Perfetto on the authorised test build; retain timestamped measurements rather than inferring totals from separate runs.
2. **Disabled launch:** cold launch the normal gate-disabled configuration, navigate repeatedly through Map/Journeys/Achievements, rotate/restart and restore stale presentation preferences.
