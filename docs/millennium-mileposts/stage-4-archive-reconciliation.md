## Architecture and inactivity

Reuses the existing `JourneyStore` atomic JSON archive, stable journey IDs, `fileToken`, Stage 2 native adapter/WGS84 evaluator, Stage 3 SQLite ledger and Android `JobScheduler`. There is no second journey store, achievement engine, backend or raw-location upload. New classes are `MilepostArchiveReader`, `MilepostCandidateBounds`, `MilepostReconciler` and `MilepostReconciliationJob`. Existing production edits are limited to the ledger, evidence adapter and a permission-protected job declaration in the manifest. The workflow and three test classes provide validation.

**No app lifecycle calls `schedule`.** A future separately reviewed integration can explicitly request the idle/charging job. A requested run can retry bounded slices; it is neither periodic nor persisted across reboot. An OS stop/process interruption preserves SQLite progress for a later explicit request/retry. Scheduling is inactive in the shipping app. There is no award, celebration, map unlock, Utilities or NCN consumer. No catalogue is downloaded or installed by this job. The real 889-row catalogue still has zero eligible physical markers; the job cannot approve them. Synthetic approval exists only in isolated test databases, using `fixture:` identities and never modifying catalogue bytes.

## Small durable archive change feed

The smallest complete feed uses **reconciliation of committed files**, rather than adding another observer to every save/delete/correction path. Normal captures, matching updates, user corrections and existing imports already replace files through `JourneyStore.save`; `delete`, mode deletion and `deleteAll` remove those files. Existing atomic replacements use monotonic modification times and `fileToken` includes size/file identity where available. No source timestamps are used as ledger version numbers.

`archive_source(user,id,stamp)` stores one compact stamp per observed identity, including deleted identities. The stamp pins projection, validator and policy revisions plus the committed file token. On a changed stamp, an atomic SQLite transaction increments that journey's durable ledger version, replaces/retracts its prior proofs through Stage 3 `sourceChanged`, and stores the acknowledged stamp. A crash cannot acknowledge a feed change without the corresponding proof invalidation. Repeated unchanged stamps cause no decoding or version increment. Tombstones retain version history; an explicitly restored higher-version file can regain the same physical recognition ordinal.

Separate durable live-file and known-source keyset cursors detect newly saved files and deletion/correction of previously observed files. Each slice handles at most 32 live files, 32 known-source checks and four ledger pages. Directory enumeration retains only the next 32 names; no `JourneyStore.all`, all-summaries list or all geometry graph is used. Enumeration itself is O(directory entries) per slice, not a permanent private spatial index. A normal source update is observed at the next relevant reconciliation pass, not synchronously at save/delete. This latency is safe for the inactive ledger; a future entitlement reader **must reconcile/fence archive freshness before publishing**. Do not treat old ledger snapshots as current live entitlements.

A name inserted behind a running cursor is found on the next sweep/request. A concurrently removed/replaced file stops the slice without advancing the affected cursor; retry observes the final committed state. Catalogue revisions use Stage 3's existing monotonic installation, immediate proof invalidation and requeue. The archive feed does not need to decode unchanged sources merely to detect a catalogue update. Revision upgrades in the projection/validator also change source stamps, making bounded reassessment explicit.

## Projected evidence and the memory incident

The previous achievement OOM involved full-road JSON graphs retained across the scan together with serialized identity copies; `LandmarkEvidence.cover` was the final failed allocation, not proof of the underlying retained owner. This worker does not call the achievement calculator or retain roads, matched traces or archive-wide geometry. SQLite retains compact proof fields, not observation arrays. Only one source is decoded at a time and at most 16 selected markers/results are retained for each ledger page.

The reader opens one committed descriptor under the existing archive monitor, then streams outside it. It never upgrades/migrates source records. Only native-adapter inputs are projected. Matcher output is reduced to the exact metadata and boolean match-presence check already used by Stage 2; no invented coordinates enter the adapter. Proximity uses the retained native observations exclusively. The presence witness is included in the canonical evidence token. Timeline preservation envelopes are skipped and are never promoted to validated evidence.

Decoder limits: 8 MiB total input read, 150,000 retained value nodes, 10,000 elements per retained array, depth 12, 512-character retained scalar/key limit. The existing adapter retains its 10,000-point ceiling, strict mode/provenance checks, resolved quality, aligned coordinates/samples, local movement and gap rules. Oversized or malformed projections become pending evidence without truncation, sampling, source reconstruction or fallback to full JSON. One selected scalar can allocate up to the total byte ceiling before its scalar limit is checked; this is bounded, not a claim of zero allocation. Skipped trees incur streaming I/O but are not retained. Larger records require a separately validated chunked reader; they are not silently eligible.

No static geometry cache is introduced. Workload metrics report complete Robolectric process heap, including framework/SQLite/test caches; they are not an isolated feature heap or ART peak. A sampled peak is a lower bound, not exact allocation tracing. The retained heap and pre-run heap include other tests in the same process. The focused Android/Robolectric test worker is capped at 256 MiB in CI, including the framework overhead and full-inventory workload. The existing 64 MiB pure streaming evaluator probe remains in CI. Device heap/PSS, repeated jobs under pressure and simultaneous Achievements/map/capture are separate acceptance requirements.

## Spatial correctness and efficiency

The ledger adds `marker_bounds(lat,lon,id)`. The worker forces that range index for its candidate query, then keyset-pages selected identities. It does not run the exact proximity evaluator against the entire catalogue for every journey. Source-level pending evidence needs no marker cross product. Each supported finite edge contributes a conservative cap about its first endpoint with surface radius `edge length + 100.001m`.

For WGS84, both principal radii of curvature are at least approximately 6,335,439m. Dividing surface distance by the smaller 6,335,000m constant gives an outward central-angle bound. Every point of an admitted edge and its 100m neighbourhood lies in that cap by the triangle inequality. Cap latitude/longitude extrema, pole coverage and date-line splitting provide conservative inclusion. Bounds include the Stage 2 numerical tolerance plus outward margin. Unsupported/malformed/long edges fall back to the exact evaluator, never a negative spatial result. Disconnected sections only enlarge the selection envelope; the exact validator receives the original disconnected edges.

The complete journey envelope can admit extra candidates on long or widely disconnected recordings; that costs exact checks but cannot award proximity across a gap. Final authority remains unchanged Stage 2 WGS84 distance and dated physical eligibility. Random deterministic tests cover 100.00001m buffers at multiple finite-edge positions/bearings, ±180° longitude, both poles and high/low latitude. Integration tests exercise actual SQL selection and lifecycle. The full 889-row inventory workload places synthetic native routes around all marker positions, rather than benchmarking only empty distant bounds. These volume fixtures have five native observations per journey; separate ceiling tests exercise 10,000/10,001 observations, and the retained pure-JVM probe exercises 802,500 edges. They do not reproduce the owner’s private geometry distribution.

## Capture priority and transactions

The job has charging and device-idle constraints, one low-priority thread per active run, four-page maximum and a two-second cooperative deadline. It never changes capture state, sampling, notification or service lifecycle. Its guard reads the existing `roadprints_capture_state.active` state and latches observed capture starts. Capture start, OS stop, deadline and thread interruption yield cooperatively. Guards/listeners/executors are released per run. A stopped job never signals completion for a replacement run.

Projection and WGS84 work run outside the archive monitor and outside ledger transactions. Feed and result writes share the same SQLite-before-archive lock order. The SQLite writer is acquired **before** taking the archive monitor, so waiting for a concurrent catalogue/feed writer cannot block capture on the archive monitor. Immediately before committing a page, a short archive-monitor fence rechecks the descriptor stamp and cancellation, then lets Stage 3 atomically check source version, evidence token, catalogue revision and marker cursor and commit up to 16 results. This closes the save/delete versus proof-commit race. The source-feed acknowledgement also uses a short monitor/transaction fence. SQLite/catalogue installation never parses journeys while holding that monitor. Existing catalogue-install/retraction operations remain the Stage 3 bounded-catalogue operations, not new capture callbacks.

The deadline is cooperative, not a hard 2s upper bound on synchronous adapter validation, SQLite I/O or an individual geodesic iteration. Device lock hold time and capture latency must be measured before scheduling is activated. The benchmark's maximum commit-monitor duration covers feed acknowledgement and result commits, including monitor acquisition wait plus commit work; it is a workstation observation, not a UI-blocking guarantee. A concurrent-correction test saves through real `JourneyStore.save` from another thread while exact proximity runs, and rejects the superseded proof before commit.

## Correctness demonstrations

- Real archive save → projection → native validator → candidate query → transactional ledger result.
- Repeated unchanged processing decodes no source and adds no proofs.
- Correct sole/selected support → pending/retracted result; an independent supporting journey survives.
- Delete one support → deterministic fallback; delete final support/delete-all → withdrawal.
- Explicit restoration/reprocessing → original recognition ordinal and first-recognised time retained.
- Restart after 32/35 archive ingress rows and 64/70 marker results → durable continuation; unfinished source summaries withheld.
- Source mutation during proximity/catalogue replacement during assessment → stale page rejected and retried.
- Capture/deadline/cancellation → no committed partial page; subsequent retry does not duplicate discovery.
- Additive Stage 3 derived schema upgrade → recognition/proofs remain intact; archive bytes untouched.

Schema 2 adds only two derived feed/cursor tables and one public-marker index to the Stage 3 local database. No production instance or existing user archive is migrated by this session. Unsupported schema transitions preserve the database by refusing to open it. Downgrade remains unsupported, so rollback means leaving the inactive database intact and disabling its caller, not deleting history.
